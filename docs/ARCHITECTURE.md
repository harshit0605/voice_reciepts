## Posting and synchronisation

A command has a unique ID, occurrence timestamp and validated operation. A database transaction takes a business-scoped advisory lock, loads that business, applies the reducer, and writes changed entities plus the command receipt. A completed checkout creates invoice, payment/credit entries, order completion, audit and stock movements together. Retrying the same ID and payload returns the stored result; changing its actor or payload is rejected. Owner approval is checked against kind, order version and approved amount.

Invoices snapshot supplied items, selected batches, prices, tax and business details. Money is integer paise; Decimal.js handles quantity conversions and rounding. Corrections are explicit returns, reversals or approved movements. The shared cash ledger attributes recorded actions; the closing shortage remains a drawer-level result. Staff count the drawer blind (the employee projection drops expected cash and differences), and each opening is compared with the cash left at the previous close. Closing the last drawer appends a report revision for every day it was open that has no report or has changed since its last one. EOD starts provisionally and waits for every non-revoked phone to acknowledge an empty outbox after the report cutoff. Successful acknowledgement appends a confirmed revision. A merely recent pre-close heartbeat is insufficient; a transaction that happened before a report's cutoff but arrived after it creates a new provisional revision and a review.

Each entity collection is a separate PostgreSQL table with `(business_id, id)` primary key, revision and JSONB payload. Auth tables are relational Better Auth tables. Reads use repeatable-read snapshots. Every external route derives business access and role from the authenticated membership. Employee projections remove purchase costs, margins, owner reviews and unrelated bills. Document paths are generated by the server and job ownership is checked before download. Public registration is blocked.

`GET /api/v1/sync?since=N` returns changed authorised records and null tombstones for records no longer visible, within a consistent snapshot. Mobile keeps the last server snapshot separately from the locally projected cash outbox. Initially it downloads an authorised state snapshot. The pilot reducer currently loads an entire tenant aggregate for posting; benchmark the real shop catalogue and history, then introduce indexed domain repositories before claiming suitability for larger chains or long histories.

On native cash checkout, an exclusive SQLCipher transaction saves the next invoice sequence, complete command, authorisation lease and local projected state **before** displaying success. Sequence keys include the Indian fiscal year and registered device. Retries never allocate a new number. Cash commands replicate to the gateway when reachable, then the server; statuses distinguish local, gateway-backed, server-synced and owner-review records. Cloud synchronisation retries on foreground and every 30 seconds while active. It does not depend on precise background scheduling.

The server validates the signed lease's business, user, device and occurrence window. It accepts completed offline cash sales even when stock is now insufficient or cached prices are stale, preserving the original bill and opening review cases. Invalid/revoked submissions are retained for owner recovery. Owner rejection is acknowledged to the original outbox and retained in the server audit. Deleting a phone's data before either backup succeeds can still lose transactions.

Online actions retain one uncertain command ID until a retry resolves it. Credit, approvals, purchasing, password changes and handoff require the server. Handoffs use order versions and recipient acknowledgement; the prior collector cannot bill a transferred order.

## API map

All application routes are under `/api/v1`. Auth uses `/api/auth/*`. A temporary password is replaced through `POST /api/auth/change-password`: the server always signs out every other session, returns the replacement session cookie, and clears the temporary-password requirement only after a successful change (`apps/api/src/auth.ts`).

| Route                                          | Access / purpose                                                                                                   |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `GET /me`                                      | Current user and memberships                                                                                       |
| `GET /state`, `GET /sync?since=`               | Membership-scoped snapshot / incremental changes                                                                   |
| `POST /commands`                               | Validated catalogue, order, money, approval, inventory and report operations; see `packages/core/src/contracts.ts` |
| `POST /sync`                                   | Signed, idempotent offline cash ingress; per-entry acknowledgement                                                 |
| `POST /devices/register`, `/devices/heartbeat` | Register own phone, renew lease, counter assignment, backlog / freshness                                           |
| `POST /employees`, `PATCH /employees/:id`      | Owner provisioning and collection/access permissions                                                               |
| `POST /recovery/import`                        | Owner imports signed local gateway backups into review after phone loss                                            |
| `GET /operations`                              | Owner queue, device and gateway health                                                                             |
| `POST /recovery/:id`                           | Owner accepts or rejects a retained offline submission with evidence                                               |
| `GET /reports`, `/invoices/:id/receipt`        | Owner aggregates and authorised invoice HTML                                                                       |
| `POST /extractions`, `GET /extractions/:id`    | Private audio/invoice upload and job status                                                                        |
| `GET /documents/:id`                           | Owner-only supplier document                                                                                       |
| `POST /gateway/observations`                   | Authenticated gateway-only observations / coverage events                                                          |

Gateway routes: `/health`, signed `/backup`, operator-only `/backups`, signed `/print`, `/prints/status`, `/prints/reprint`, operator-only `/camera/events` and `/camera/clips`, owner-lease `/clips/:id` and `/clips/:id/preserve`.

Gateway access uses the device's signed lease; operational camera ingress uses a separate server-side token. A lease is a 24-hour capability: revocation while the gateway is fully isolated is not instantaneous. This deployment uses HMAC lease verification on a trusted, access-controlled gateway; isolate it and protect its signing secret. An asymmetric signing-key migration is advisable before distributing appliances to unrelated operators.

## AI and camera boundaries

Sarvam Saaras v3 receives only explicitly recorded sale dictation. Gemini produces schema-validated, reviewable item or purchase drafts. A valid schema is not a correctness guarantee. Product matching never substitutes or auto-posts. Uncertain medicine name/strength/form/unit must be resolved by the dispenser. Provider implementations are replaceable in `apps/api/src/providers.ts`.

The owner operations endpoint exposes extraction queues and gateway freshness. Request logs include status and elapsed time; extraction results include elapsed time and provider token usage. Gateway heartbeats report printer configuration/backlog and camera forwarding backlog. After a previously connected gateway misses 90 seconds of heartbeats, the worker creates an owner coverage review.

The worker claims jobs with `FOR UPDATE SKIP LOCKED`, automatically retries transient provider failures at most once, with owner-requested invoice retries capped at three total attempts, and reclaims abandoned locks. Job rows survive API/worker restarts. Camera video is processed locally. Only anonymous counter/time observations reach the API; matching bills are candidates, not proof. The detector requires operator-provided ONNX weights and recorder access. Camera process supervision, hardware sizing and stream-specific reconnect tuning depend on the recorder audit.

## Deliberate pilot limitations

- No production cloud stack, signing accounts, real merchant integration, subscription billing or full accounting is provisioned.
- Owner review and approval notifications are in-app with foreground refresh. Background push delivery is not implemented; camera employee notifications are deliberately absent.
- GST invoice handling currently assumes local, intra-state, tax-inclusive pharmacy sales (CGST/SGST). Interstate/IGST, cess, tax-filing exports and specialised Schedule X records are not supported. Block those operational scenarios at onboarding.
- Core screens are bilingual; provider error strings and some dynamic administrative diagnostic text remain English. Native Hindi receipt shaping and font availability require physical verification.
- Camera clips are short excerpts (up to approximately 20 seconds before interaction end), not full-visit evidence. A partial clip cannot establish that a purchase occurred.

## Receiving refinements

See [FEATURE-PASSES.md](FEATURE-PASSES.md) and [AI-COSTS.md](AI-COSTS.md). `GET /api/v1/extractions` lists resumable owner invoice jobs and monthly job usage; `POST /api/v1/extractions/:id/retry` retries a failed invoice within the attempt cap. The upload transaction serialises a business-scoped content-hash lookup and allowance check. Source document IDs are verified against completed invoice jobs in the same business before purchase posting. Native draft autosave uses the existing encrypted KV store, scoped to business and owner; web preview remains memory-only. Source fields and the confirmed unit conversion are saved on purchase lines. Invoice-level freight/round-off/discount adjustments require a reason and are separate from batch costs.

## Voice draft lifecycle

`POST /api/v1/extractions` accepts voice audio with a UUID `saleId` and positive client-reported `recordedSeconds` up to 30. `POST /api/v1/extractions/text` accepts `{text, saleId}` without STT. Both return an idempotently reused or newly queued job. `GET /api/v1/voice-jobs` lists only the current actor's 20 recent jobs; `GET /api/v1/extractions/:id` exposes a saved transcript for authorised recovery. Owner extraction usage includes reservations and speech-call attempts.

The worker checkpoints successful STT in PostgreSQL before structure extraction and removes audio immediately afterward. Exact catalogue text may use a deterministic parser; other transcripts use the replaceable structure provider. Retries read the saved transcript. The shared voice output schema is validated before review. No generated item is automatically billed.

Mobile sale entry persists the basket, remaining voice items and job identifier as one serialized snapshot scoped to business/member. Adding a reviewed item consumes it in the same snapshot; catalogue, unit, quantity and physical batch remain staff decisions. Recovered nonempty baskets require checking Orders before collecting again. This is a human recovery gate, not a cross-device checkout ownership protocol. The web preview uses memory storage; native storage uses existing encrypted SQLite.
